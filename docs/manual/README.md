# Руководство игрока

PDF о том, как играть в текущую версию «Связки». Его не пишут заново при каждом изменении: он собирается из живой игры.

```bash
npm run manual
```

Результат — `docs/manual/out/svyazka-manual.pdf`. Папка `out/` в git не хранится. При каждой отправке в `main` руководство собирается на GitHub и лежит в артефактах запуска (вкладка Actions → запуск → `svyazka-manual`).

Для сборки нужен Chrome. Если он стоит не в обычном месте, укажи путь: `CHROME_PATH=/путь/к/chrome npm run manual`.

## Как это устроено

Сборщик поднимает игру на копиях примеров из `examples/`, сам проходит по экранам, проживает пример хода и снимает экран после каждого шага. Поэтому снимки и цифры всегда из той версии игры, которая лежит в репозитории.

| Файл | Что в нём | Когда править |
|---|---|---|
| `manual.md` | Текст: посыл игры, глоссарий, как строится карта, терминал, где живёт игра | Изменилась идея, появился термин, поменялись команды |
| `screens.ts` | Экраны и их блоки: что показывает, откуда данные, зачем; действия на экране | Появился, изменился или исчез блок или действие |
| `story.ts` | Пример хода: шаги, их текст и проверки | Изменились правила хода, цены действий, пример `examples/demo` |
| `build.ts` | Сборщик: снимки, вёрстка, печать | Меняется устройство руководства, а не игра |
| `manual.css` | Вид страницы | То же |

## Что страхует от устаревания

Руководство не может молча отстать от игры. Три проверки:

1. **Блоки.** Каждый блок экрана помечен в интерфейсе атрибутом `data-block`, и руководство находит его по этому имени. Блок переименовали или убрали — тест `apps/web/test/manual.test.ts` падает в `npm run check` и называет блок.
2. **Пример хода.** Каждый шаг в `story.ts` — настоящие действия в интерфейсе с проверками: «после 1on1 в шапке 4/8», «сигнал ушёл». Правило изменилось — сборка останавливается и называет шаг и то, что увидела вместо ожидаемого.
3. **Вставки.** Неизвестная вставка `{{…}}` в `manual.md` — ошибка сборки.

Чего проверки не ловят: смысл. Если блок остался на месте, но стал показывать другое, описание в `screens.ts` надо поправить руками.

## Что делать при изменении игры

| Что изменилось | Что сделать |
|---|---|
| Новый блок на экране | Дать ему `data-block` (у `Panel` — свойство `block`, на листе — `name` у `Block`) и добавить запись в `screens.ts` |
| Блок убрали или переименовали | Тест назовёт его: убрать или переименовать запись в `screens.ts`, проверить шаги в `story.ts` |
| Новое действие | Добавить строку в `actions` нужного экрана; если оно стоит внимания — показать в примере хода |
| Изменились цены или правила хода | Сборка упадёт на шаге примера: поправить текст и ожидания шага в `story.ts`, а заодно цены в `manual.md` |
| Новый экран | Добавить его в `SCREENS`, вставку `{{screen:<id>}}` в `manual.md` и строку в таблицу экранов там же |
| Новый термин | Строка в глоссарии в `manual.md` |
| Изменился пример `examples/demo` | Пересобрать; если шаг примера хода перестал сходиться, поправить `story.ts` |
| Закрыт шаг плана сборки | Поправить `GAME_STATE` в `screens.ts` и раздел «Чего пока нет» в `manual.md` |

После любой правки: `npm run manual` и просмотреть PDF глазами. Вёрстка проверяется только так.

## Про снимок штурмана

При сборке настоящие модели не вызываются: ключей у сборщика нет и быть не должно. Ответ штурмана на снимке составляет сам сборщик из тех же данных игры (`standInAnswer` в `build.ts`), и в руководстве это прямо сказано.
