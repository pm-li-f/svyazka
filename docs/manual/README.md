# Руководство игрока

Готовое руководство — [`docs/svyazka-manual.pdf`](../svyazka-manual.pdf). На обложке указано, какую версию игры оно описывает.

**Руководство обновляется только по явной просьбе владельца проекта**, а не с каждым изменением игры. Пока такой просьбы нет, ни PDF, ни файлы в этой папке не трогаем.

Когда обновить попросили, его не пишут заново: оно собирается из живой игры.

```bash
SVYAZKA_MANUAL=1 npm test       # сверить описанные блоки с интерфейсом
npm run manual                  # собрать в docs/manual/out/ и посмотреть глазами
npm run manual -- --publish     # то же и положить результат в docs/svyazka-manual.pdf
```

Папка `out/` в git не хранится. На GitHub руководство можно собрать вручную: вкладка Actions → `manual` → Run workflow; PDF появится в артефактах запуска.

Для сборки нужен Chrome. Если он стоит не в обычном месте, укажи путь: `CHROME_PATH=/путь/к/chrome npm run manual`.

## Как это устроено

Сборщик поднимает игру на копиях примеров из `examples/`, сам проходит по экранам, проживает пример хода и снимает экран после каждого шага. Экраны и ход снимаются на `demo`; блоки Jira и Confluence — на `jira-pomnit-vse`; заставки и эффекты — кнопками предпросмотра на вкладке «настройки». Поэтому снимки и цифры всегда из той версии игры, которая лежит в репозитории.

| Файл | Что в нём | Когда править |
|---|---|---|
| `manual.md` | Текст: посыл игры, глоссарий, как строится карта, терминал, где живёт игра | Изменилась идея, появился термин, поменялись команды |
| `screens.ts` | Экраны и их блоки: что показывает, откуда данные, зачем; действия на экране. Там же `SOURCE_BLOCKS` — блоки, которые появляются с Jira и Confluence, и `SPLASHES` — заставки | Появился, изменился или исчез блок, действие, заставка |
| `story.ts` | Пример хода: шаги, их текст и проверки | Изменились правила хода, цены действий, пример `examples/demo` |
| `build.ts` | Сборщик: снимки, вёрстка, печать | Меняется устройство руководства, а не игра |
| `manual.css` | Вид страницы | То же |

## Что страхует от устаревания

Руководство не может молча отстать от игры. Три проверки:

1. **Блоки.** Каждый блок экрана помечен в интерфейсе атрибутом `data-block`, и руководство находит его по этому имени. Блок переименовали или убрали — тест `apps/web/test/manual.test.ts` называет его. Тест запускается только с `SVYAZKA_MANUAL=1`: в обычной проверке его нет, чтобы работа над игрой не требовала правок руководства.
2. **Пример хода.** Каждый шаг в `story.ts` — настоящие действия в интерфейсе с проверками: «после 1on1 в шапке 4/8», «сигнал ушёл». Правило изменилось — сборка останавливается и называет шаг и то, что увидела вместо ожидаемого.
3. **Вставки.** Неизвестная вставка `{{…}}` в `manual.md` — ошибка сборки.

Чего проверки не ловят: смысл. Если блок остался на месте, но стал показывать другое, описание в `screens.ts` надо поправить руками.

## Что делать, когда попросили обновить

Сначала посмотри, что изменилось в игре с коммита на обложке PDF, затем пройди по таблице.

| Что изменилось | Что сделать |
|---|---|
| Новый блок на экране | Дать ему `data-block` (у `Panel` — свойство `block`, на листе — `name` у `Block`) и добавить запись в `screens.ts` |
| Блок убрали или переименовали | Тест назовёт его: убрать или переименовать запись в `screens.ts`, проверить шаги в `story.ts` |
| Новое действие | Добавить строку в `actions` нужного экрана; если оно стоит внимания — показать в примере хода |
| Изменились цены или правила хода | Сборка упадёт на шаге примера: поправить текст и ожидания шага в `story.ts`, а заодно цены в `manual.md` |
| Новый экран | Добавить его в `SCREENS`, вставку `{{screen:<id>}}` в `manual.md` и строку в таблицу экранов там же |
| Новый блок, который виден только с источниками | Запись в `SOURCE_BLOCKS` в `screens.ts`: он снимется на примере `jira-pomnit-vse` |
| Новая заставка или новый повод для эффекта | Запись в `SPLASHES`; список поводов для эффектов — в `gameLayerHtml` в `build.ts` |
| Новый термин | Строка в глоссарии в `manual.md` |
| Изменился пример `examples/demo` | Пересобрать; если шаг примера хода перестал сходиться, поправить `story.ts` |
| Закрыт шаг плана сборки | Поправить `GAME_STATE` в `screens.ts` и раздел «Чего пока нет» в `manual.md` |

После правок: `npm run manual`, просмотреть PDF глазами (вёрстка проверяется только так) и опубликовать с `--publish`.

## Что сборщик не трогает

Настоящий файл ключей при сборке не читается, в Jira и Confluence сборщик не ходит: вход в источники у него — заглушка, а данные — готовые снимки из примера.

## Про снимок штурмана

При сборке настоящие модели не вызываются: ключей у сборщика нет и быть не должно. Ответ штурмана на снимке составляет сам сборщик из тех же данных игры (`standInAnswer` в `build.ts`), и в руководстве это прямо сказано.
